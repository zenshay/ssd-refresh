## 決定與理由

正式發版改用較省時的跨套件最佳化方式（ThinLTO），並分成 16 份工作。
本機開發與 PR 保留既有開發設定。
本機 `--release` 與遠端發版共用根目錄 Cargo.toml 的設定，方便重現正式產物。

目標是把時間用在推進專案，而不是讓每次修改都等待完整發版建置。
三個流程用途不同，不必使用相同的最佳化設定。

| 流程 | 做什麼 | 等待邊界 |
|---|---|---|
| 本機修 bug | 開發模式，重用上次編譯的細部資料，稱為增量編譯 | commit 不等待遠端 CI |
| 同步與 PR | push 保存進度；PR 執行既有完整檢查 | 合併前才需要最新檢查通過 |
| 累積更新後發版 | 版本標籤觸發檢查、各平台建置及草稿驗證 | 這時才建立交付使用者的產物 |

額外的發布模式驗證只有手動啟用 `release_builds` 時執行。
一般 PR 會略過，不新增每次 push 的發版建置。
工具鏈、依賴版本、出錯清理行為與正確性檢查維持原樣。

## 為什麼選 44 秒方案

14 秒與 44 秒是兩個候選，不是同一設定的兩個結論。

| 候選 | 各自同機基準 | 候選重編時間 | 少等多久 |
|---|---:|---:|---:|
| ThinLTO，保留一份 | 138.313 秒 | 123.872 秒 | 14.441 秒，10.4% |
| ThinLTO，分成 16 份 | 169.004 秒 | 125.070 秒 | 43.934 秒，26.0% |

每個條件重編三次，取中間值。兩組使用不同型號的主機，不能直接比較兩個基準。
負載是修改共用 Rust 檔案註解後，重建 GUI、CLI 與合成效能測試程式。
這不是任意真實修改或完整發版的保證速度。
執行效能負載為 8 MiB 合成資料指紋與 1 萬列 CSV，每個迴圈至少執行 700 毫秒。
編譯器記憶體每 200 毫秒抽樣一次，不是整台機器的保證峰值。

16 份方案的已量代價如下：

- GUI 多約 1.20 MB。
- 編譯器抽樣記憶體多 453 MiB，約 475 MB。
- 暫存編譯產物多約 252 MiB；這不等於 GitHub 上傳快取的增量。
- 每 1 萬列合成表格多約 0.43 毫秒，約 5.6%。每個條件交錯測九次。
- 合成資料指紋與列數核對通過；指紋吞吐速度幾乎相同。

使用者接受這些絕對代價，選擇較大的編譯收益。
初篩百分比只作提示，不因增加 13% 容量或表格慢 5.6% 就自動淘汰。
仍要看實際多幾 MB、幾毫秒，以及整輪少等幾秒。
功能測試失敗則不能採納。

開發版增加分工沒有縮短完整驗收。nightly 的收益不足以支持額外維護。
Cranelift 未通過 Windows 出錯清理測試，因此沒有採用，也沒有放寬測試。
完全關閉 LTO 的合成執行成本較高，且沒有追加同機確認。
保留一份的 14 秒方案只作保守備選。

## 整輪發版省時仍是推算

歷史暖快取工作：x64 260 秒、ARM64 289 秒。ARM64 的編譯部分為 212 秒。
兩者同時執行，要等較慢的工作。只加速 x64，仍會等 ARM64。

模型以檢查 258 秒、最慢建置 289 秒、歷史其他開銷 39 秒相加，得到 586 秒。
若兩種 Windows 工作都少 44 秒，整輪模型少約 7.5%。
若兩種架構的編譯部分都快 26%，整輪模型少約 55 秒，約 9.4%。
這些資料來自不同工作與版本。完整新版本標籤的端到端收益尚未實測。
ARM64 的 26% 加速也仍是假設，不能把建置成功當成加速證明。

## 已驗證與未驗證

[採納驗收](https://github.com/zenshay/ssd-refresh/actions/runs/41281946938)的 12 個執行工作全數通過。
包含既有完整檢查、Windows x64 最佳化建置與測試、ARM64 建置與測試程式交叉編譯。
Linux 與 macOS 的最佳化 CLI 建置與測試也通過。
合併前的八個一般 PR 檢查均通過。

[合併後 main 驗收](https://github.com/zenshay/ssd-refresh/actions/runs/41282453857)的十個執行工作均通過。
兩份 Windows 發布依賴快取已準備完成，沒有為此建立版本標籤或發布 release。

未做 ARM64 實機、真實磁碟、需管理員權限的磁碟映像、斷電復原與本機重編效能測試。
合成表格慢 5.6% 不代表整個程式或 SSD 操作慢 5.6%。

## 生命週期與還原

首次變更可能使快取失配，需要重建依賴。新舊快取可能暫時並存。
日常不新增 commit／push hook，也不讓普通 PR 建立發布產物。
維護同一份正式設定，不增加 nightly、新快取服務或付費 runner。
換 Rust、依賴、主機或架構時重新量測，不沿用舊數字作保證。
停用時把 release 改回 `lto = true`、`codegen-units = 1`；可能需要重建快取。
程式資料格式沒有改動，不需遷移資料。

官方文件與 Tauri、Zed 的實例列在英文紀錄。用途分模式是既有設計，具體數值沒有社群統一標準。
